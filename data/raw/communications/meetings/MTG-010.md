If we use GET, we have to pass the user ID and filters in the URL. With complex filters—like the ones we need for role-based access—the URL becomes monstrous.   }

# Meeting Summary
The team reviewed and finalized the API design for the Orion retrieval service. They decided on using POST requests for queries to ensure security and flexibility. A standardized JSON response envelope was defined, including a specific section for evidence and metadata to support citation validation and performance tracking. Error handling was standardized around custom codes, and the a versioning strategy using URL prefixes (`/v1/`) was adopted.

# Decisions Taken
1. **HTTP Method:** Use `POST /v1/query` instead of GET to avoid leaking IDs in logs and handle complex filters.
2. **Response Envelope:** Standardized JSON envelope including `answer`, `citations`, and `metadata` (latency, strategy, cache status).
3. **Evidence Tracking:** Include the full list of evidence chunks passed to the LLM in the response for server-side validation.
4. **Abstention:** Lack of information should be a successful 200 response with an abstention message, not a 400/500 error.

# Open Issues
1. **Filter Complexity:** Need to define the exact JSON schema for the `filters` object to ensure it's compatible with the ChromaDB adapter.
2. **Rate Limiting:** No discussion yet on how to implement rate limiting per user or per API key.
